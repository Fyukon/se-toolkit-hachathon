# Конкретный план создания проекта

## 1. Идея проекта

Проект представляет собой ассистента для студента, который работает с данными из SingularityApp и помогает:

- смотреть понятную сводку дня и недели;
- видеть важные задачи и ближайшие дедлайны;
- позже изменять расписание и задачи через команды на естественном языке.

Продукт должен состоять из:

- backend;
- database;
- клиентского интерфейса;
- интеграции с SingularityApp API;
- интеграции с LLM.

---

## 2. Как продукт будет работать

### Сценарий Version 1

1. Пользователь подключает свой аккаунт SingularityApp.
2. Backend получает события и задачи из SingularityApp API.
3. Данные приводятся к единому внутреннему формату.
4. Нормализованные данные сохраняются в базу данных.
5. Пользователь открывает клиент и нажимает `Показать мой день` или `Показать мою неделю`.
6. Backend собирает актуальные данные за нужный период.
7. LLM формирует короткую и понятную сводку.
8. Клиент показывает пользователю готовый результат.

### Сценарий Version 2

1. Пользователь вводит команду вроде `перенеси мою встречу на 2 часа позже`.
2. Backend отправляет текст команды в LLM или специальный сервис разбора команд.
3. Сервис превращает запрос в структурированное действие.
4. Backend находит нужное событие или задачу.
5. Backend проверяет конфликты и корректность изменения.
6. Пользователь получает экран подтверждения.
7. После подтверждения backend применяет изменение через SingularityApp API.
8. Результат сохраняется в БД и показывается пользователю.

## 3. Архитектура проекта

Проект лучше строить как 4 основных слоя:

### 3.1. Клиент

Это интерфейс, через который пользователь взаимодействует с системой.

Варианты:

- простой web-клиент;
- Telegram Mini App.

Для хакатона лучше начать с web-клиента, потому что:

- он проще в разработке и отладке;
- не зависит от ограничений Telegram bots на университетских VM;
- его проще быстро задеплоить.

### 3.2. Backend

Backend отвечает за:

- аутентификацию пользователя;
- работу с SingularityApp API;
- синхронизацию событий и задач;
- работу с БД;
- генерацию сводок через LLM;
- разбор команд на изменение расписания;
- подтверждение и применение изменений.

### 3.3. Database

База данных нужна для хранения:

- пользователей;
- токенов доступа;
- событий;
- задач;
- ранее сгенерированных summary;
- черновиков изменений;
- логов действий.

### 3.4. Внешние интеграции

Нужны две внешние интеграции:

- `SingularityApp API` для получения и изменения расписания;
- `LLM API` для генерации summary и разбора естественного языка.

## 7. Основные backend-модули

### `singularity_client.py`

Отвечает за прямую работу с API SingularityApp.

Должен содержать методы:

- получение токена;
- обновление токена;
- загрузка событий;
- загрузка задач;
- изменение события;
- создание или изменение задачи.

### `sync_service.py`

Отвечает за синхронизацию данных.

Должен:

- получать данные из внешнего API;
- приводить их к внутреннему формату;
- сохранять их в БД;
- обновлять существующие записи.

### `summary_service.py`

Отвечает за формирование данных для summary.

Должен:

- выбирать события и задачи за день или неделю;
- считать окна свободного времени;
- определять перегрузки и ближайшие дедлайны;
- формировать структурированный контекст для LLM.

### `llm_service.py`

Отвечает за вызовы LLM.

Должен:

- принимать структурированные данные;
- отправлять их в модель;
- получать summary или структурированный разбор команды;
- логировать ответы и ошибки.

### `action_parser_service.py`

Отвечает за разбор текстовых команд пользователя.

Должен:

- принимать текст команды;
- определять намерение;
- выделять тип действия;
- выделять время, дату, целевой объект;
- возвращать JSON с проектом изменений.

### `apply_changes_service.py`

Отвечает за применение изменений.

Должен:

- валидировать изменения;
- проверять конфликты;
- применять изменения через SingularityApp API;
- сохранять результат в БД.

## 10. Что реализовать в Version 1

Version 1 должна решать одну полезную задачу полностью.

### Обязательный результат

- пользователь может подключить аккаунт;
- backend умеет получать реальные данные из SingularityApp;
- данные сохраняются в БД;
- пользователь может получить summary дня;
- пользователь может получить summary недели;
- есть простой клиентский интерфейс;
- есть базовые тесты.

### Что сознательно не включать в Version 1

- автоматическое изменение расписания;
- сложную агентную систему;
- много экранов;
- сложную аналитику;
- продвинутый UI.

## 11. Что реализовать в Version 2

Version 2 должна добавить управление расписанием и довести проект до deployable состояния.

### Обязательный результат

- пользователь может вводить текстовые команды;
- команды разбираются в структурированные действия;
- backend показывает подтверждение перед изменением;
- backend применяет изменения через внешнее API;
- изменения логируются;
- проект запускается в Docker;
- проект задеплоен и доступен для использования.

### Поддерживаемые команды на старте

Лучше ограничить Version 2 несколькими сценариями:

- перенос события на другое время;
- создание новой задачи;
- перенос задачи на другой день;
- изменение времени существующего события.

## 13. Как должен выглядеть поток summary

1. Пользователь нажимает `Показать мой день`.
2. Клиент вызывает `GET /summary/day`.
3. Backend проверяет, есть ли подключённый аккаунт.
4. Backend проверяет свежесть синхронизации.
5. При необходимости backend обновляет данные из SingularityApp.
6. Backend выбирает события и задачи за текущий день.
7. Backend собирает структурированный контекст.
8. LLM формирует короткое понятное summary.
9. Клиент показывает готовый текст.

---

## 14. Как должен выглядеть поток изменения расписания

1. Пользователь вводит команду.
2. Клиент вызывает `POST /actions/parse`.
3. Backend сохраняет исходную команду.
4. Backend отправляет текст в сервис разбора.
5. Сервис возвращает структурированный draft действия.
6. Backend проверяет, найден ли нужный объект.
7. Backend проверяет конфликты.
8. Клиент показывает пользователю предварительный результат.
9. Пользователь подтверждает изменение.
10. Клиент вызывает `POST /actions/{id}/confirm`.
11. Backend применяет изменение через SingularityApp API.
12. Backend обновляет локальные данные.
13. Клиент показывает итоговый результат.

## 15. Что важно для качества проекта

### Не полагаться только на LLM

LLM должна:

- объяснять;
- суммировать;
- помогать разбирать команды.

Но backend-код должен:

- считать время;
- искать конфликты;
- выбирать конкретные записи;
- подтверждать корректность;
- применять изменения.

### Делать узкий, но рабочий сценарий

Для хакатона лучше сделать мало, но стабильно:

- хорошая summary дня и недели;
- 2-3 поддерживаемые команды изменения;
- обязательный экран подтверждения;
- понятный и быстрый интерфейс.

### Разделять этапы

Нельзя начинать с красивого интерфейса до того, как заработает:

- авторизация;
- синхронизация;
- хранение данных;
- summary endpoint.
